Giggity

Finding London gigs before they have happened or sold out.

Why I built it & what I wanted

I kept running into the same frustrating cycle: hearing that a band I love had played in London the previous evening, or clicking a ticket link only to find the room sold out three weeks ago. Following individual venues meant checking ten different websites every Sunday afternoon, bookmarking fragmented pages, and trying to remember what had changed since the week before.

I wanted something simple and practical:

  • One unified calendar combining major commercial feeds with independent, grassroots room listings.
  • An interactive venue map so I could explore what was playing nearby without clicking back and forth across different promoters.
  • A clean change log tracking newly announced gigs, rescheduled dates, or doors time adjustments without turning every page refresh into false updates.
  • Offline-first reliability with zero heavy server dependencies, so the listings stay fast and accessible from anywhere.

The goal was straightforward: go to more gigs without spending hours wrangling tickets. The data plumbing grew from solving the messy realities of event feeds.

Data source hurdles & why 3 venues, then 10

Relying solely on commercial ticket APIs (like Ticketmaster Discovery) only captures large rooms and touring acts, completely missing grassroots venues. Meanwhile, independent venue websites publish listings however their CMS pleases: custom HTML markup, nested WordPress loops, or embedded JSON-LD schemas.

Rather than trying to scrape 50 venues on day one and building something fragile, I started with 3 venues (Union Chapel, Colour Factory, and Roundhouse). That forced me to settle a few basics first:

  • Strict balance accounting: Every collection run requires that fetched = accepted + rejected. If an upstream API query caps out, the ingest worker splits the date window into smaller intervals until every unique event ID is accounted for.
  • Fail-closed triage: If a parser hits an unexpected HTML layout, unknown event category, or unmapped coordinates, the run stops and keeps the existing database untouched instead of writing bad rows.
  • Bot walls: Several London venues sit behind strict anti-bot checks or CAPTCHAs. Rather than writing brittle proxy workarounds, those venues were put on a separate list to look at later.

Once those checks worked reliably, I expanded collection to 10 venue programmes (adding KOKO, Blue Note, O2 Academy Islington, O2 Academy Brixton, and others). When an unhandled format or mixed bill turns up, it gets flagged in venue-review-needed.json for a quick manual check before staging.

Tracking changes without inventing cancellations

A classic bug in event scrapers is treating a disappeared listing as a cancellation. Upstream APIs drop records temporarily during maintenance, paginate unevenly, or swap event IDs during promoter updates. Inferring that a concert has been cancelled just because it wasn't returned on today's run creates noisy, false alarms.

When an upcoming event is absent from today's collection, Giggity keeps its prior observation timestamp and status untouched. Absence is never treated as cancellation.

Local state lives in standard-library SQLite (var/events.sqlite3) with versioned schema migrations. To power the /changes feed without false updates, each gig is fingerprinted using a cryptographic hash over only the core factual attributes fans care about: artist title, performance date, doors time, venue identity, price range, and ticket seller URLs. Non-semantic details (such as image CDN tokens, query ordering, and collection timestamps) are normalized out, so only genuine date changes, venue moves, or on-sale announcements trigger a change log entry.

How it actually works

From local data collection and review to global edge deployment.

Why each major tool

Every tool in the stack was chosen to keep complexity bounded, eliminate server maintenance, and avoid cloud lock-in:

Python 3.12 & Pydantic v2
The collection and ingestion engine. Pydantic guarantees that dates, UK timezone transitions (GMT/BST), doors times, and price ranges are strictly validated before anything touches the database. If an API contract drifts, Python fails fast.
Local SQLite (events.sqlite3)
Stores canonical event records, venue identities, and cryptographic comparison hashes without running a heavy database server or paying for cloud databases. Versioned schema migrations track state locally.
Local AI Agents (Ollama)
Supplementary local intelligence using vision and embedding models (such as qwen2.5-vl). Used as a bounded, offline fallback for messy flyer and poster text extraction, or scoring ambiguous deduplication candidates when regex matching is inconclusive. AI never writes directly to canonical data without human review.
SvelteKit (Static Adapter)
The public frontend. All search, filtering, calendar navigation, and change tracking run client-side in the browser against the exported JSON snapshot. Zero runtime server load and sub-second page transitions.
MapLibre GL & OpenFreeMap
Fast vector map rendering for London venues. MapLibre tiles load only when you open the venue map, keeping the initial page weight tiny.
Cloudflare Worker, R2 & D1
The edge serving layer. A Cloudflare Worker routes traffic to the static SvelteKit app, serves immutable event snapshots directly from R2, and queries a D1 database pointer to determine the active release.

Why Cloudflare Worker & edge hosting

A major architectural decision was completely decoupling the public demonstration from the private ingestion machine:

  • Total server isolation: The public site does not connect to my home workstation, local database, or private API keys. Even if my computer is switched off, the site stays online on Cloudflare's edge.
  • Immutable snapshot releases: Publishing uploads a versioned snapshot to Cloudflare R2 and flips the release pointer in Cloudflare D1. Rolling back is instantaneous.
  • Polite visitor gate: Rather than forcing visitors through intrusive third-party CAPTCHAs, a small Worker prompt asks first-time visitors for their intent, records the timestamp in D1, and sets a signed 24-hour cookie. This keeps automated scrapers away without frustrating people.
  • Zero hosting bills: With static caching and minimal Worker CPU time, running costs stay basically at zero.

Future plans

Giggity is actively evolving. Priorities on the immediate roadmap include:

  • Personal calendar export (.ics): One-click calendar feeds for followed venues and saved gigs.
  • Targeted change notifications: Opt-in push or email notifications specifically for newly added dates, moved shows, or price updates on followed artists.
  • Grassroots venue expansion: Extending direct programme parsers across independent East and South London venues as parsers prove reliable over multi-month runs.
  • Structured flyer intake: Maturing the local Ollama vision pipeline to allow dropping a venue poster or social graphic into the collector for automated date extraction and review.
