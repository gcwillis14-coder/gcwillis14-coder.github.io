Giggity

Finding London gigs before they have happened or sold out.

Open Giggity ↗ All projects →

Why I’m building it

I kept hearing about gigs a day after they had happened or once tickets had already gone. Following individual venues meant checking half a dozen calendars and remembering to come back to them a week later.

Giggity pulls London listings into one place with a venue map and a change log so I can see what has been newly announced, moved or put on sale. The original requirement was simple: go to more gigs. The data plumbing grew from there.

Collecting from uneven sources

Relying on a single ticket feed misses smaller rooms, while venue websites publish in whatever format suits their CMS. A Python collector combines the Ticketmaster Discovery API with direct HTML and JSON programme parsers for seven London venues: Union Chapel, Roundhouse, KOKO, Colour Factory, Blue Note, O2 Academy Islington and O2 Academy Brixton. A few other venues sit behind bot challenges; those stay on a deferred watchlist rather than being worked around.

Provider search APIs also cap how many records a single query can return. When a London date window gets close to that limit, the collector splits the interval into smaller windows until page totals and unique source IDs balance. Every record fetched in a run is accounted for as accepted or rejected, whether it is an internal DO NOT PURCHASE test listing, a duplicate or a venue outside London. If a collection stops early or fails its balance checks, it fails closed and leaves the existing dataset untouched.

Sorting gigs from everything else

Venue calendars rarely separate live bands from club nights, comedy, film screenings, theatre workshops or talks. Treating every entry on a venue’s What’s On page as a gig fills the list with noise, while aggressive keyword filtering quietly drops real shows.

Before venue listings reach the database, a local triage step (giggity/venue_merge.py) classifies each programme item. It reuses prior review decisions when an event’s core details have not changed, auto-accepts dedicated music rooms (such as Blue Note and the two O2 Academy venues) or listings that match an existing Ticketmaster URL, and filters explicit non-gig phrases using whole-word boundaries. That boundary rule came from early mistakes: naive substring checks for art and musical tried to throw out Arctic Monkeys, Art Garfunkel and Musical Youth.

Where a bill genuinely mixes formats, such as a comedy night with live jazz, a multi-day festival pass, or a listing whose details have shifted since it was last reviewed, the pipeline stops and writes it to venue-review-needed.json for a quick manual decision before anything is staged.

Tracking changes without inventing cancellations

One of the earliest design choices was how to treat a listing that disappears from a feed. APIs drop rows temporarily, paginate oddly or swap event IDs when a promoter updates a tour. Inferring a cancellation simply because a listing was absent from today’s run produces false alarms. When a future event is not seen in a collection, Giggity keeps its previous observation timestamp rather than marking it cancelled.

Local state lives in standard-library SQLite (var/events.sqlite3) with versioned schema migrations. When the same show appears on both Ticketmaster and a venue calendar, the store links them under one canonical event while keeping source provenance separate so primary fields are not silently overwritten.

To power the /changes page without turning every refresh into an update, each event is hashed using only the fields a gig-goer cares about: title, date, doors time, status, venue, price range and ticket URLs. Whitespace and list ordering are normalised and collection timestamps are ignored, so the change log only records genuine additions or changed details.

One contract between Python and the browser

The local pipeline and the web app meet at a single versioned file, events.json. Rather than hoping the frontend agrees with whatever Python exported, both sides validate the same snapshot contract (giggity/models.py in Pydantic and apps/web/src/lib/snapshot.ts in TypeScript) against shared test fixtures.

The contract checks chronological ordering, Europe/London GMT and BST offsets, reconciled quality and provenance counts, and strict https: URL parsing that rejects malformed links before a snapshot can be published.

From local review to map

Collection, triage and publishing run locally through a justfile (just collect, just review, just publish). API keys stay in Proton Pass or the system keyring rather than .env files, and raw API archives are redacted before they touch disk.

The frontend is a static SvelteKit app. Search, date filters, source filters and the change log run entirely in the browser against the published snapshot without a live database server. MapLibre GL and OpenFreeMap vector tiles are loaded via dynamic import only when you open the venue map, keeping the initial page light and leaving the listings usable if map tiles fail to load.

Publishing uploads a verified snapshot to Cloudflare R2 and updates a release pointer in Cloudflare D1. A small Worker sits in front of the site and /events.json with a D1-backed visitor gate and signed cookie, enough to deter casual scraping without adding third-party CAPTCHA scripts.

Listings remain dated observations rather than live ticket inventory or complete London coverage. It is always worth checking the venue or ticket seller before making plans.

Tools and structure

Collection & storage
Python 3.12 · uv · httpx · Pydantic v2 · SQLite (var/events.sqlite3)
Web application
SvelteKit (static adapter) · TypeScript · MapLibre GL · OpenFreeMap · Node test runner
Hosting & release store
Cloudflare Workers · D1 (release pointer & visitor gate) · R2 (immutable snapshot releases)
Local workflow & secrets
just task runner · Proton Pass CLI & Fedora Secret Service · bounded read-only MCP inspector for ad-hoc API checks
Key modules
giggity/collect.py (window splitting & Ticketmaster ingest) · giggity/venue_merge.py (programme triage & merge) · giggity/storage.py (SQLite migrations & change hashes) · apps/web/src/lib/snapshot.ts (browser contract validator)

Still being worked on

I’m gradually adding more independent London venues and tidying awkward duplicate cases where promoters bill support acts differently across sites. Collection stays manual for now while I see which venue parsers stay reliable over a few months of programme changes.
